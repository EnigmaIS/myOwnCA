Key material & recovery

HSM & Keys

Hardware security module

HSM status not loaded yet.

Unlock token PIN

The User PIN is held only for your session and dropped on logout, lock, or restart.

Who may unlock the token

Certificate Operators issue certificates, so by default they may unlock the token to sign with it: the operator whose approval mints a certificate is asked for the User PIN at that moment. Administrators can always unlock.

Turn this off only to enforce separation of duties, where the operator authorizes issuance and an administrator controls the key. Operators are then told to ask an administrator to unlock, and their approval is not recorded until the token is open.

Cloud keys & signing queue

Private keys remain non-exportable. Transient signing failures retry for up to 24 hours; jobs delayed for 15 minutes are operational alerts. There is never a local-key fallback.

Token keys

Retirement uses a fixed 30-day grace period. Managed keys are destroyed by the cleanup worker only after the deadline; attached/external keys are detached. Native SmartCard-HSM backups are available below when the token has a complete DKEK.

DKEK recovery disabled

This token was initialized without DKEK shares. Its Sub CA key cannot be wrapped, recovered, or migrated to another HSM. Enabling migration requires destructive token reinitialization and replacement of the Sub CA.

DKEK backup shares

DKEK shares are created only during Setup. SmartCard-HSM DKEK is N-of-N: every share has its own password and needs redundant copies in separate locations. Deleting a server copy never deletes external copies.

DKEK status not loaded yet.

Export native HSM backups

Requests one untouched OpenSC SmartCard-HSM .bin file per live token key in a plain ZIP transport. A different administrator must approve the request; the approving administrator unlocks the User PIN before the archive is generated. The archive contains no DKEK shares, passwords, PINs, database state, or application metadata.

      Random number source

      Software key generation always uses the OS CSPRNG; bytes from an external device (e.g. /dev/trng, /dev/hwrng) are mixed in additively before each generation — server-generated keys, sub-CA keys, and service-cert keys alike. PKCS#11 tokens use their own hardware RNG. A configured but unreadable device blocks generation (fail-closed).

      Secure links for certificate holders

      Holder portal

      Link composition & delivery

      Public base URL used to compose secure claim links sent to certificate holders. Download receipts email the holder whenever a key-bearing bundle is fetched through a link.

      Holder portal status not loaded yet.

      Renewal links prefer mTLS proof-of-possession: terminate client-cert TLS on a reverse proxy and forward the cert with the shared secret (see "Reverse proxy (mTLS) setup"). Without it, renewals fall back to email codes + mandatory Certificate Operator approval.

      The 30 days start when the final active binding is removed by revocation, expiry, replacement, archive, cancellation, or rejection. This grace period cannot be bypassed.

      How holders use it

      Certificate Operators send single-purpose claim links (delivery, renewal, enrollment) from their portal; unknown people can apply via the public request-access page. Links require an email verification code; tokens are stored hashed and can be revoked at any time from the Certificate Operator portal's Secure links panel.

      Delivery integrations

      Connect email, SMS, Slack, webhooks, or custom HTTPS delivery. Message content and recipients are supplied per send.

      Advanced integration field referenceRaw configuration keys for API and troubleshooting use 
      email config: {"host","port","security":"none|starttls|ssl","username","from_address"}
email secrets: {"password"}

sms config: {"url","method":"POST|GET|PUT","recipient_param","message_param","extra_params":{},"headers":{},"body_template"}
sms secrets: {"bearer_token","password"}  (recipient: phone)
  GET sends the parameters in the query string; POST/PUT send them in the body,
  form-encoded when Content-Type is application/x-www-form-urlencoded, else JSON.
  extra_params carries the broker's static fields (account, sender, type); a value
  may reference {password} or {bearer_token} so the credential stays encrypted
  rather than sitting in the cleartext config. Headers are HTTP headers, not
  broker parameters. Defaults are to=phone and message=text; body_template
  overrides the parameters and is rejected with GET, which has no body.
  Example (curl -d user=... -d pass=... -d number=... -d text=...):
    method POST, Content-Type: application/x-www-form-urlencoded,
    phone parameter "number", message parameter "text",
    extra parameters: user=myaccount / pass={password} / type=sms / from=MyName

slack secrets: {"bot_token"}  (recipient: handle, email, or user id)
  bot token scopes: chat:write, im:write, users:read, users:read.email
  (reinstall the Slack app after changing scopes; the token value changes)

webhook config: {"url"}
webhook secrets: {"signing_secret"}  (optional HMAC)

https config: {"url","method","headers":{},"body_template"}
https secrets: {"bearer_token"}  (optional)
body_template placeholders: {recipient} {subject} {body}
