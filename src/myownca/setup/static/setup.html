Install type

Pick Test/Lab to evaluate, Production for real use.

Learn more

Test/Lab — for evaluation: a throwaway CA can be auto-generated and a one-click issuer is available; not for certificates anyone should trust. Production — for real use: you import your own offline-generated root (below) and the full issuing-CA ceremony applies.

Root CA certificate import

Paste your offline-generated root cert for Production.

Learn more

Your trust anchor. In Production you generate the root offline (air-gapped) and import only its certificate here — the root private key never touches this server. In Test/Lab, leave blank and a throwaway CA is created.

OpenSSL helpers — run these on the offline Root CA machine

Keep root-ca.key offline. Only paste the resulting root-ca.crt into this setup wizard.

1. Generate an encrypted RSA Root CA key

openssl genpkey \
  -algorithm RSA \
  -aes-256-cbc \
  -pkeyopt rsa_keygen_bits:4096 \
  -out root-ca.key

2. Create the self-signed Root CA certificate

openssl req -new -x509 \
  -key root-ca.key \
  -sha256 -days 3650 \
  -out root-ca.crt \
  -subj "/C=PL/O=Example Organization/CN=Example Root CA" \
  -addext "basicConstraints=critical,CA:TRUE,pathlen:1" \
  -addext "keyUsage=critical,keyCertSign,cRLSign" \
  -addext "subjectKeyIdentifier=hash" \
  -addext "authorityKeyIdentifier=keyid:always,issuer"

Issuing Sub CA key storage

      
This choice applies only to the Issuing Sub CA signing key. Leaf certificates are not stored in HSM or cloud: with a user-provided CSR, the private key stays with the requester; server-generated leaf keys are kept encrypted locally.

      
Learn more
        
The Issuing Sub CA signs the leaf certificates, but its private key is kept separately
        from all leaf private keys. Choose local storage for an offline installation, or a cloud
        provider for a non-exportable Sub CA key. The PKCS#11 User PIN is never saved; admins
        unlock the token from the portal when needed.

            AWS identity and policy helper
            
Create a dedicated IAM identity with an access key, then replace
            YOUR_REGION and YOUR_ACCOUNT_ID in the bootstrap
            policy. Use the same region in the form below.

            
Policy while myOwnCA creates and manages signing keys

            
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowListingKmsKeys",
      "Effect": "Allow",
      "Action": "kms:ListKeys",
      "Resource": "*"
    },
    {
      "Sid": "AllowCreatingTaggedKmsKeys",
      "Effect": "Allow",
      "Action": [
        "kms:CreateKey",
        "kms:TagResource"
      ],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:RequestTag/myownca:managed": "true"
        },
        "ForAllValues:StringEquals": {
          "aws:TagKeys": [
            "myownca:managed",
            "myownca:label"
          ]
        }
      }
    },
    {
      "Sid": "AllowManagedKmsKeyUseAndLifecycle",
      "Effect": "Allow",
      "Action": [
        "kms:DescribeKey",
        "kms:GetPublicKey",
        "kms:Sign",
        "kms:ScheduleKeyDeletion",
        "kms:CancelKeyDeletion",
        "kms:EnableKey"
      ],
      "Resource": "arn:aws:kms:YOUR_REGION:YOUR_ACCOUNT_ID:key/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/myownca:managed": "true"
        }
      }
    }
  ]
}

          OpenSSL helper — sign this CSR on the offline Root CA
          
Use this for a CSR generated by myOwnCA. The -copy_extensions copy
          option preserves the required Sub CA BasicConstraints and
          KeyUsage; without it OpenSSL silently drops them.

          
openssl x509 -req \
  -in sub.csr \
  -CA root-ca.crt \
  -CAkey root-ca.key \
  -out subca.crt \
  -days 1825 -sha256 \
  -copy_extensions copy

Initial administrator accounts

      
Choose a governance mode to see how many distinct administrators are required.

      
Learn more
        
Dual control requires two distinct administrators so the proposer cannot approve
        their own governed role grant, password/TOTP reset, or governance downgrade.
        Single-administrator mode permits one bootstrap admin, but removes that second-person
        barrier for role grants and password/TOTP resets. Every admin sets a new password and
        enrolls TOTP MFA at first login.

      

      
Temporary passwords are generated below. Record each enabled account's password and
         deliver it only to that administrator; it must be changed at first login.
